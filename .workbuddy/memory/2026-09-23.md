## Phase 6 GameEvent 重写（完成）
`npm run verify` → 7 文件 / 74 用例全绿；`npm run build-only` exit 0；type-check 0 错。

### 落地形态
- **两套状态分离**（这是历史 bug 的根源）：`status/stage` 是流水线位置，只有调度器改；`finished/step` 是事件内容状态，内容自己改。混用会出「步骤跑完事件就终态、后续 After 技能全不触发」这类问题。
- **步骤机**：`addStep(n, fn)` 注册，`runSteps()` 在 Content 阶段由调度器驱动。`goto()` 会置 `stepMoved` 标志抑制自动前进，所以 `goto(0)` 成环合法。**迭代实现不递归**（不爆栈），用 `MAX_STEP_ITERATIONS = 256` 预算兜底无出口循环 → 抛 `EventStepOverflowError`。
- **`finish()` vs `cancel()` 语义分开**：finish 只跳过剩余步骤，End/After 照常；cancel 跳过全部后续阶段直接进终态。forced 事件 cancel 是空操作。
- **状态机**：主链相邻推进 + 「任意非终态 → 终态」（无懈可击的前提）。非法转移抛 `EventTransitionError`。踩过的坑：一开始加了「已终态就拒绝任何转移」的守卫，结果 `cancelled → completed` 被自己拦了 —— 改成靠 `CHAIN_NEXT` 表（`cancelled: [completed]`）判定，不再单独设终态守卫。
- **`trigger(name, data)`**：建子事件 → addChild → 交给 `IEventRunner` 调度并 await。运行器由 EventDispatcher 在 dispatch 时注入 `event.runner`，**结算后解绑**；未注入时抛 `EventRunnerMissingError`（不静默）。深度守卫在 dispatch 与 trigger 两条入口都有。
- `core/event/errors.ts`（新）：`EventError` 基类 + `EventNestingError` / `EventStepOverflowError` / `EventRunnerMissingError` / `EventTransitionError`。禁止裸 `new Error('[EventDispatcher] ...')`。
- 便捷访问全是**视图不是副本**：`target`≡`targets[0]`、`card`≡`cards[0]`、`num`↔`values.num`（读写同一份，避免两个真值源）、`depth` 由 parent 链推导、`result: EventResult` 可写 bool/cards/targets/num + 任意自定义字段。
- 顺手修的 bug：**`event.stage` 从来没被更新过**（一直是初始 'Begin'），调度器现在逐阶段赋值。
- `player` 未显式传入时继承 `source`（此前 phase-manager 等多数发射点只传 source，player 一直是 undefined，'player' 监听范围形同虚设）。
- `canceled` → `cancelled`（对齐无名杀拼写）；`isFinished` → `isTerminal`；`EventChain.depth` → `size`。
- `EventPauseManager` 暂停粒度改为**单个事件**：`pause(eventId, reason, timeout)` / `resume(eventId)` / `isPaused(eventId)` / `getPendingEventIds()`。effect-context 的 waitForResponse 已跟进传 `this.event.id`。

### 关键设计（别退回老路）
**每张无懈都是一条真 `useCard` 事件**，不是给原事件记个数。只开一层窗口，更深的层由那张无懈自己的内容再调 `openCancelChain()` 打开——事件嵌套代替手写递归，**栈就是链**。一层只接受一张无懈（`stopOnFirstResponse`），有人出手就上移一层，并从**那张无懈的使用者**的下家重新绕一圈（官方规则）。

### 踩过的坑（重要）
1. **测试牌定义必须带 `CardTag.Trick`**。无懈可击本身是锦囊——少了这个标签它就不开第二层窗口，链长永远是 1。真实牌定义（`source/cards/tricks.ts`）有，但测试里手搓的 `cardDef` 容易漏。
2. **`cancelable` 必须在事件上显式打开**。content-registry 那条老测试造了个裸事件就指望被抵消，Phase 9 起必须写 `cancelable: true`。
3. **Edit 工具并行改同一文件会静默丢一次**。本轮有两次「成功」提示但内容没落盘（game-engine 的 import、game-event 的字段声明），都是 type-check 才暴露出来的。同一文件的多次 Edit 要串行。
4. 日志/文档里写反引号会被 Bash shim 当命令替换吃掉——追加记忆日志别用 `node -e` 拼字符串。

### 与计划的两处偏差（已写进 refactor-plan Phase 9）
1. 抵消目标用 `data.counterTarget` 显式传递，而非计划里写的「父事件的父事件」（一层抵消实际消耗两层嵌套：`useCard` + 卡牌事件，靠树结构推算必错）。
2. 链的形状由事件嵌套表达，不额外维护栈深度计数；`cancelDepth` 只是观测编号。奇偶是结果，不是机制。

## Phase 10 — 伤害流水线统一（已完成）

**结论：144 用例全绿 / type-check 0 错 / build 通过 / lint 28 存量（新增文件 0 告警）**

### 做了什么
- 删掉 `core/system/damage-system.ts`（含 `DamageStage` / `DamageInstance` / `DamageHook` / `registerHook`），
  新建 `core/system/damage-resolver.ts`：`DamageResolver` 全是静态方法，只回答「最终伤害多少」「扣完剩多少血」。
- `EffectContextDeps.damageSystem` 改名 `damageResolver`；`GameEngine` 同步（字段 + import + 构造 + deps）。
- `EffectContext.damageTarget()` 不再扣血、不再跑并行流水线：只发一条 `damage` 事件，
  并用 `parent: this.event` + `addChild()` 挂到发起方事件树上（`sha → damage → dying` 链可读）。
- `IEffectContext` 新增 `applyDamage(target, amount)`——伤害扣血的**唯一**对外入口，实现直接转 `DamageResolver`。
- 新增 `source/base/contents/damage-content.ts`：步骤机四步（常量 `DAMAGE_STEPS`）
  `Resolve(1)` 数值定稿 → `Source(2)` 发 `damageSource` 子事件 → `Apply(3)` 唯一扣血 → `Dying(4)` 发 `dying` 子事件求桃。
  注册为 `['damage', damageContent]`。
- `damageSource` 加进 `POINT_EVENT_NAMES`（单发事件）。
- 【闪】从 `parent.prevented = true` 改为 `parent.cancel('闪')`；【杀】被闪抵消时也 `cancel()` 掉自己。
- 新测试 `src/__tests__/event/damage-pipeline.test.ts`（14 例）。

### 关键设计（别退回老路）
- **伤害就是普通事件**，不再有平行流水线。想改伤害就在 `damageBefore` 写 `event.values.extraDamage`。
- **真值源只有 `values.num`**：进来是基础值，`Resolve` 步之后是最终值；`baseDamage` 只作事后回溯，不参与计算。
  旧代码的 `DamageInstance.currentAmount` 与 `event.num` 双真值源正是病根。
- **防止伤害 = `cancel()`**（跳过 Content 之后全部阶段，damageEnd/damageAfter 不误触发）；
  直接置 `prevented` 只跳过扣血，后续阶段照常——这两者不是一回事。

### 踩过的坑（重要）
1. **Edit 工具并行改同一文件会静默丢一次**（第 3 次中招）。本轮 `game-engine.ts` 的 `new DamageSystem()`
   和 `contents/index.ts` 的 `['damage', damageContent]` 都被吞了，全靠跑测试才暴露。
   **同一文件的多次 Edit 必须串行。**
2. **`ctx.event.name` 恒为事件主体**（`'damage'`），阶段后缀不在名字里。
   写「记录各段顺序」的测试时，日志要记**注册的那个事件名**（`damageBefore`），否则全记成 `damage` 看不出分段。
3. **`damageTarget` 之前用 `dispatch()` 直接发，导致伤害事件不是发起方的子节点**——
   测试里按 `children` 找 `damage` 找不到。已改为显式 `parent` + `addChild`。

### 与计划的两处偏差（已写进 refactor-plan Phase 10）
1. `damageSource` 做成单发子事件而非阶段名（`damage` + 后缀推导不出来，且它一次伤害只发一次）。
2. 伤害点数单真值源 `values.num`，`baseDamage` 降级为回溯字段。
