### 四个真问题

1. **夹取规则各写各的。** `recoverHp` 知道不能超上限，濒死救活的 `hp = 1` 不知道——
   它只是碰巧在 hp ≤ 0 时才被调用。现在 `resurrect` 独立成方法：
   它是「设为」不是「回复」，因为溢出伤害能把 hp 打到负数，`recoverHp(1)` 救不回来。
2. **「非正数」防线只写在一条路上。** 原来只 `DamageResolver` 挡着，回血没人管，
   `recoverHp(-2)` 返回 -2 → 日志写出「回复了 -2 点」。现在收进写入点，三条路同规则。
3. **「有第二条路」比「第二条路写错了」更危险。** `Player` 上那 10 个方法生产代码
   **一个都没人调用**，只在测试里被用。判定标准改成：
   **零引用的写入方法一律删，不留「以后可能用得上」。**
4. **删完要有测试记住「不许再加回来」。** `player-system.test.ts` 末尾的结构护栏
   断言 `Player` 上不存在那批方法、`PlayerSystem` 里没有卡牌区域写入。

### 踩到的坑

- **`settleDying` 双重弃牌**：`DeathSystem.handleDeath` 现在自己把牌送进弃牌堆，
  调用方还在对同一批牌再弃一次 → 「弃置弃牌堆里的牌」报错（6 个测试挂在这里）。
- **oxlint `expect-expect` 看不见辅助函数里的断言**：把断言写进 `expectVisibleTo()`
  这类 helper 会被判「测试没有断言」。直接内联。
- **`@tests` 路径别名不存在**：测试里引脚手架要用相对路径 `'../helpers/game-env'`。
- **`isVisibleTo` 只在 `Card` 实体上**，`ICard` 接口只暴露 `visibleTo` 数组。测试照接口写。

### 一处刻意的例外

`DeckManager.draw()` 仍写 `card.zone = Hand`——它是「两步式」交接：牌堆只摘牌，
交到谁手里由 `CardSystem.obtainCards()` 完成（摸牌数与「摸给谁」由不同层决定）。
漏掉第二步不报错、牌只是消失，因此契约写进文档注释，三个调用点紧挨着写，
并由「开局发牌后全场三处账目一致」做全表兜底。
`phase-manager.ts:291` 的 `zone === Processing` 分支依赖 `drawForJudge()` 的同样标记，
故未一并改动——风险大于收益。

## Phase 20 —— 日志与可观测性 ✅

**结果**：`test` 363/363（新增 17 例）· `type-check` 0 · `oxlint` 0 · `eslint` 0 · `build` 通过

### 新增

- `src/core/debug/event-trace.ts` —— 事件嵌套树。`EventDispatcher` 加三个回调
  （进流水线 / 换阶段 / 离流水线），按 `parent` 组装成树，节点带事件名、参与者、
  卡牌、数值、阶段序列、终态、逻辑刻度；`toJSON()` 导出 + `render()` 文本。
- `src/core/debug/mod-trace.ts` —— 每次 Mod 查询的 `base → 每个修改器 → result`，
  未参与的也留痕并写明原因（`owner-dead` / `filtered-out` / `short-circuited`）。
- `src/core/debug/index.ts`、`src/core/contracts/trace.interface.ts`（两个 sink 契约带 `enabled`）
- `src/__tests__/debug/observability.test.ts`（16 例）
- `GameEngine.setObservability({ trace, mods })` 总开关，**默认全关**

### 日志底板

`LogEntry.timestamp`（墙钟）→ `tick`（逻辑刻度）。`GameState.addLog` 自己盖章，
调用方**传不进时间**；墙钟由呈现层 `logStore.addLog` 补（`ViewLogInput` 允许不带 `tick`，
因为「正在初始化游戏」这类不在任何一局内部）。两个视图里 13 处 `timestamp: Date.now()`
由脚本统一剔除。

### 两个真问题

1. **「日志不影响确定性」这条验收，被它自己的验收测试打破了。**
   开着观测跑两遍导出的事件树对不上——不是观测改了行为，是
   **`GameEvent` 的 id 生成器从来没被归零过**。Phase 18 只归零了 `Card._idGenerator`，
   而 `GameEvent.resetIdGenerator()` 明明写好了，就是没人调用。
   于是「录的是 event_1…、放的是 event_546…」，而事件树导出里带着 id。
   → 补进 `GameEngine.init()` 的归零清单，并加注：
   **任何会被写进可比对外延的自增量都得在清单里，清单要集中，不能散在各文件的 `resetXxx()`。**
2. **观测端必须彻底旁观。** 三个 trace 回调在引擎侧一律吞错（「因为树记不下去
   导致整局崩了」承受不起）；记录时只读 `gameClock.now` 不调 `next()`
   （观测拨时钟 → 后续事件时间戳整体错位）。

### 设计要点：关着的观测必须与不存在等价

「开关」不是「记完丢弃」，而是从一开始就不往下走。因此 `candidates()` 的
跳过原因用回调传出而非返回两组数组——关着的调用方不该为一份不要的信息多分配对象。
`dispatch` 里三个 notify 也不包闭包。

### 踩到的坑

- `ModQueryInfo` 定义在 `trace.interface.ts` 而非 `mod.interface.ts`，导入位置写错（tsc 挡住）。
- `src/core` 里残留的 `Date.now()` 只剩三处诊断用途（boot 日志、AI `decisionLogs` 耗时、
  `randomSeed()` 无种子兜底），均不进游戏状态——`logFingerprint` 早剔除 id 与时间戳。
