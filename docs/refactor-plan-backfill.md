**来源与适用修订**：本文件由第三方在 2026-09-29 通读 `docs/refactor-plan.md`（当时 1640 行）
后写成，**只读了文档、没有交叉核对 `src/**`**。因此：

- 唯一的例外是「背景」一节里那份基线实测表——它是对计划 §0 转述，也请一并确认。

## 背景与动机

`docs/refactor-plan.md` 的正文（各 Phase 的「落地情况」「与计划的偏差」「真问题」）质量很高，
是该文档最有价值的部分。但**汇总层已经和实际脱节**，具体四处：

1. **§3 进度总表不可信**：✅ 标记位置不统一，已完成的 Phase 漏标，Phase 4B 整行缺席，
   图例里的 ⬜ / 🟡 从未被使用过。
2. **§4 组 F（Phase 21–27）的「现状 / 问题」列是过期快照**——写于组 C/D 完成**之前**，
   多条断言与已通过的验收直接冲突。
3. **全局约束第 4 / 5 条被破过，破例没有登记**（「不留欠账到下个 Phase」「未通过验收不得进入下一 Phase」）。
4. **§2「扩展能力验收清单」28 条自称总验收标准，却一个勾选都没有**；
   而 §5 里程碑表据此宣称 M4 已达成。

这四项不修，会有两个具体后果：

- Phase 21 开工后第一件事会变成「重新确认哪些其实已经做完」，而不是做事；
- 计划 `:1610` 明确把 **M4 定为「建议的最小交付」**，而 M4 是否真达成，**当前文档无法回答**。

## 硬约束（违反即任务失败）

- **只改文档**：`docs/refactor-plan.md`，必要时 `docs/code-standards.md`。
  **不得改动 `src/**`、测试、脚本、构建配置**。
- **一切结论以代码为准。** 本文件列出的可疑点来自纯文本阅读，可能是错的。
  每条都必须用 `grep` / 读实现实证后再下笔。**文本与代码冲突时，以代码为准。**
- **不做功能改动、不做重构、不新增 Phase、不调整 Phase 顺序与依赖。**
  若发现硬冲突（例如依赖已被别的 Phase 覆盖），**只记录，不改动**。
- **不删减**已有的「与计划的偏差」「真问题」「实现记录」——它们是本文档的核心资产。
- 行号会漂移：编辑后一律按 **Phase 标题 / 小节标题** 锚点定位。
- 沿用以有排版风格：中文、表格用于枚举、`**加粗**` 用于强调、
  验收项一律写成 `- [ ]` / `- [x]`。
